## 一、问题与方法

作者固定源码的安全投影配置为`max_particles=1<<20`、`max_blocks=1<<25`；[碰撞能量实现](../../reference/近期强基线_20260908/pamo/simp_cuda/safe_project/src/pamo_safe_project/energy.py)用`max_blocks`作为多个碰撞核函数的启动维度，包括CG反复调用的`collision_hess_dx_kernel`。27号表明BVH构建、更新和查询不是本批小网格的主耗时项，本轮遂量化CG中的启动规模。

在用户提供的同一RTX 4080 SUPER上，先用[核函数观察脚本](profile_pamo_cg_kernels.py)记录`crossing_e1`的第二次CG求解；第一次用于CUDA Graph捕获。PyTorch profiler会显著增加主机侧墙钟，故只比较这次求解中报告的核函数GPU时间与调用次数。Nsight Compute因实例未开放GPU性能计数器而不能采集访存计数，本轮**没有证明访存带宽瓶颈**。两次运行的阶段三活跃顶点约718/698，工作量接近但输出并不逐点相同。

随后在两条已见解析C1开发路线的八张冻结Geogram网格上，顺序执行“原版→接触容量65536→原版→顶点容量16384→原版”，每组每张运行一次。所有组均使用预加载CPU模块、逐帧派生独立CUDA子进程、作者三阶段、`ratio=1.0`和`min_vertex=0`。接触容量变体沿用26号隔离副本；顶点容量变体由[生成脚本](prepare_pamo_particle_capacity_variant.py)从作者包复制，仅改一行配置，保留接触容量、迭代次数及能量。作者配置SHA256为`df1eb24db57394c32e31f6d67a58cd7ef6c25febc11aff39c5e9503ee82d6390`；两个变体的哈希见[原始记录](实验结果/20260929_容量与核函数局部性诊断/)。

## 二、核函数轨迹

| 第二次CG求解，单张`crossing_e1` | 原版 | 接触容量65536 |
| --- | ---: | ---: |
| GPU事件数 | 487 | 487 |
| 全部GPU事件累计 | 4.73 ms | 1.62 ms |
| 碰撞Hessian向量乘，40次累计 | 3.152 ms | 0.043 ms |
| 清零核函数，162次累计 | 0.632 ms | 0.633 ms |
| 铰链Hessian向量乘，40次累计 | 0.558 ms | 0.557 ms |

碰撞Hessian核函数的启动维度随容量从33554432降到65536，约缩小512倍；该核函数的累计GPU时间约下降73倍。这是**单次求解的设备活动时间**，不可外推成整帧73倍加速。观察性profiler记录的两次CG墙钟约872/876 ms，远大于GPU事件时间之和，包含插桩、主机调度及同步等开销；两者不能当成未经插桩的CG耗时。原始轨迹分别位于[默认容量](实验结果/20260929_容量与核函数局部性诊断/cg_kernel_trace_crossing_e1_20260929/profile.json)和[65536容量](实验结果/20260929_容量与核函数局部性诊断/cg_kernel_trace_64k_crossing_e1_20260929/profile.json)。

## 三、完整帧容量对照

| 顺序 | 配置 | 有效帧 | PaMO入口墙钟均值 | 内部运行均值 |
| ---: | --- | ---: | ---: | ---: |
| 1 | 原版 | 8/8 | 2515.3 ms | 1794.7 ms |
| 2 | 接触容量65536 | 8/8 | 2314.7 ms | 1587.3 ms |
| 3 | 原版复跑 | 8/8 | 2346.1 ms | 1650.3 ms |
| 4 | 顶点容量16384 | 8/8 | 2490.1 ms | 1754.4 ms |
| 5 | 原版末轮 | 8/8 | 2379.9 ms | 1675.0 ms |

第1到第3组原版自身下降169.2 ms，表明冷暖状态或运行顺序干扰显著。65536组比相邻两组原版快31.4—200.6 ms/帧，不能只报告最大的200.6 ms为容量收益。26号独立16帧实验中，65536容量较首尾原版均值约快10%；本轮仍显示可能的有限收益，但幅度尚不稳定。顶点容量16384组反而比前后原版慢约110—144 ms/帧，不保留这个变体。顺序并非随机交错，样本也只有八张已见开发网格，这些差异不能作为统计显著性或一般性能证明。

## 四、输出审计与解释边界

五组40/40张输出在[同一审计入口](audit_pamo_speed.py)下通过闭合拓扑、顶点流形、无退化面和双向8192点抽样几何检查。各组最大抽样误差为0.04755—0.06624 mm；每组最坏`<10°`三角形比例为2.157%—3.465%，最坏`<5°`为0.097%—0.393%，`<1°`均为0。接触容量65536组日志未发现容量超限或缩小检测半径重试。审计是有限抽样协议，不构成连续几何误差证明，也不保证不同输出逐点逐面一致。逐帧哈希、原始OBJ、日志及五份`*_audit.json`均在[实验结果目录](实验结果/20260929_容量与核函数局部性诊断/)内。

本轮改动是**容量与核函数启动规模的执行实验**。它没有重排网格邻接布局、实现邻域缓存或验证MeshTaichi论文的数据局部性机制；也没有实现动态网格局部并行更新。不能把前述文献方向记为已复现。对于更大骨面和更密接触，65536上限仍可能触发作者的缩半径分支，须先有安全的超限退回再用于正式方法。

## 五、下一步

1. 在不修改接触半径的前提下，实现“接触数超限则以原容量重算该帧”的隔离执行保护；先在独立冻结输入和真实CT网格上审计，再判断能否将65536作为自适应首选容量。
2. 做按输入交错的配对运行与分阶段未插桩计时，区分接触核函数、缓冲区分配、CUDA Graph捕获及启动开销，给出稳定的净收益区间。
3. 若研究MeshTaichi式数据局部性，另行改动邻接布局并设置独立消融；若研究局部动态执行，必须验证受影响区域之外的碰撞和投影约束不被遗漏。研究内容二最终仍需对完整Geogram→PaMO→状态发布的反馈序列报告时延、吞吐和状态年龄。
